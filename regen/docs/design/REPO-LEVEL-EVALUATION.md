# Repository level 证明生成实验设计

实验围绕三个问题展开：本方法在不同模型和数据集上的整体生成能力；沿用人工划分与自主划分对生成结果和 token 消耗的影响；生成的 helpers 如何被实际使用，以及 token 消耗在哪里。主要资源约束为相同生成时间，token 消耗作为结果报告，不额外要求各方法消耗相同 tokens。

## 实验矩阵与研究问题

| 实验 | 比较对象 | 固定条件 | 主要结果 |
|---|---|---|---|
| 主实验 | 本方法、通用 Codex agent、VERO | 数据集、模型配置、生成时长、硬件与并发资源上限、验收标准 | 截止时有效 contract 数量与比例，完整集成结果 |
| 划分消融 | 本方法沿用原划分、本方法自主划分 | contracts、语义基础、模型、局部生成与 helper 策略、生成时长、资源上限 | 有效 contract 数量与比例，生成阶段 tokens |
| helper 分析 | 本方法各运行，可对照两种划分 | 相同身份与引用统计规则 | 创建、证明、实际使用、共享情况及其关联目标 |
| token 分析 | 主实验和划分消融的运行 | 相同用量去重与阶段归档规则 | 输入、缓存输入、输出及可获得的 reasoning 用量；阶段分布 |

主实验使用方法 × 模型配置 × 数据集的共同可运行矩阵。一个配置应固定模型版本、reasoning 设置、上下文限制以及各角色使用的模型；如果规划器与局部 prover 使用不同模型，须将整个组合视为一个配置。记录 agent、适配层和检查器版本，特别标明 VERO 的 Isabelle 适配。

数据集覆盖 Refine、CRefine，以及待选定的初始无项目特定证明库的项目。Refine 和 CRefine 分别冻结目标集合和语义基础，CRefine 不依赖另一实验运行临时生成的 Refine。新项目仍保留解释目标所需的实现语义、定义和合法基础库。“无证明库”不意味着缺少目标的语义上下文。

正式矩阵需要冻结具体模型配置、项目清单、每个数据集的生成时长与重复次数。相同数据集内使用相同生成时长；如果不同数据集采用不同预算，分别报告，不能直接比较原始证明数量。每次运行从干净的任务状态开始，不复用其他运行的生成 helpers、证明或模型记忆。

## 主实验的输入与方法边界

三种方法获得相同固定 contracts 和语义基础，移除目标层原证明体、原 helpers 及其证明专用属性，不提供原 contract 到 theory 的归属和原 import 图。各方法从允许输入构造自己的规划；方法本身的规划、检索和生成策略保留，不要求使用本方法的内部控制流程。

检查能力、合法事实访问边界、生成目标和验收规则应对齐；适配层不能额外提供从原证明提取的目标专用提示。方法间不同的批量编辑、检索决策和检查策略属于系统差异，记录其开销。实现或资源差异可能影响结果时，应在对应配置旁说明。

当前 [Codex 入口](../../planning/generic_codex_agent.py) 和 [VERO 入口](../../tools/vero_serial_application.py) 均包含自主分组后冻结的流程。Codex 控制器默认采用 `sketch-reviewed-v1`，提示还要求在策略触发时检查 helper sketch。因此必须冻结并披露共享 harness 的策略，不能把该配置称为完全没有本方法机制的 plain agent。它可以作为较强的共享工具基线，但其差异主要体现整体控制与组织；不能用这一对照单独归因 helper 条件检查的效果。

如果某个基线入口必须接收外部划分，应明确标记为“给定规划的基线”，记录规划来源，不把该结果解释为其自主组织仓库的能力。不能只向某个方法额外提供原始人工划分，却仍将该单元称为输入相同的主实验。

## 划分消融

两组都使用本方法的相同生成器、helper 策略、工作区、检索与检查实现，并在生成前冻结 theory 边界。此消融比较划分来源，不比较生成期动态重规划。

- **沿用原划分：** 通过可信准备过程提取固定目标的原 contract 到 theory 归属，构造新的空证明工作区。只固定这一分组关系，不直接复制原 theory 源码、helpers 或证明骨架。
- **自主划分：** 从不含原始归属的公开输入生成分组，不读取原划分组的产物和历史信息。

主消融建议只将原始分组关系作为额外输入，imports 根据允许的语义信息、生成分组和共同的合法性规则构造。若同时保留原 imports，应另行标注为“沿用原架构”，因为它增加了依赖结构信息。具体选择在运行前写入配置，不在结果出来后更换。

人工分组提供了结构先验，因此本消融的准确表述是“相同目标和语义基础、不同架构先验、相同生成时长”。它不属于双方完全 owner-blind 的同输入对照，也不将人工划分视为性能上界。

主要比较生成阶段的有效 contract 数量和实际 tokens；规划时间和 tokens 单列。若两组全部完成，比较到达全部 contracts 通过及最终集成成功所需的生成时间、实际墙钟时间和成本，保留提前完成的实际消耗，不为凑满预算继续运行。

## 生成时间与截止规则

现有新入口使用有效生成时间。主协议沿用这一口径，并同时报告墙钟时间、并发 worker 累计时间及被排除阶段的耗时。固定有效生成时间不等于固定总运行时间或总计算量。

| 阶段 | 生成时间口径 |
|---|---|
| 正常模型推理、编辑、helper 工作、检索、局部修复及普通候选原生检查 | 计入 |
| 架构规划、初始化、声明预检查、前缀或 heap 准备等受信准备工作 | 由统一 harness 事件排除并单列 |
| 受信原生 seal/build 和 repository integration | 排除并单列 |
| seal 失败后的模型诊断和证明修复 | 计入 |
| 明确记录的暂停、确认的 provider 恢复等待 | 按同一冻结规则处理，另报耗时 |

排除由 harness 的实际操作决定，不能由 agent 自报阶段标签决定。排除阶段与模型生成重叠时仍须计入活跃生成；局部分解和修复不能通过重命名为“规划”逃避预算。论文记录计时策略版本与实际排除明细。

并发运行的有效时间按活跃生成区间的并集累计，worker 累计时间另报。各方法设置相同模型调用并发上限、checker 槽位、CPU 和内存资源上限，并报告实际利用率。更高的生成吞吐量可以成为系统结果，但额外资源不能被隐藏。

整个运行共享一个生成预算，切换 theory、产生新 GREEN、重试或恢复均不重置。恢复保留历史用量和时间；确认的外部服务或宿主机故障采用事先固定的统一处理规则。系统自己的生成失败保留在结果中。

达到预算时冻结源码、接受记录、正在运行的请求及对应状态，停止新的生成和修复。统一的截止后审计只验证冻结产物，不使用反馈继续修改证明。主表的 contract 数量以截止前完成的有效检查证据为准；截止后才完成检查的候选单列，不回填成截止前成功。完整集成结果应区分截止前完成与截止后仅对冻结产物完成审计。

## 结果统计

设数据集固定目标集合为 C，N(T) 为生成预算 T 截止时具有有效原生证据的不同 contract 数量，覆盖率为 N(T)/|C|。

contract 身份以冻结输入为准，不能靠改名、重复证明或引入新声明增加数量。helper 成功、临时假设下的条件闭合、声明解析通过均不计入 N(T)。历史首次 GREEN 与截止时有效 GREEN 分列；同 theory 后续草稿失败不能抹去仍然有效的旧证据，确实受上下文修改影响的证据也不能继续计入。

主表每行至少包含：数据集、模型配置、方法、重复运行标识、生成预算、实际有效生成时间、有效 contract 数量与覆盖率、完整集成状态。sealed theory 数可以用于运行诊断，但因分组不同，不作为跨方法能力的主要指标。

每次运行绘制有效 contract 数量随生成时间的曲线，并保留证据失效导致的下降。若使用首次 GREEN 累计曲线，另行标注，不替代当前有效结果。全部完成时报告完成时间；未完成运行保留为预算内未成功，不能只平均成功运行的成本。

多个数据集分别报告结果。跨数据集汇总时同时说明按 contract 加权的覆盖率与按任务平均的覆盖率，防止较大数据集支配结论。重复运行报告单次值和离散程度，不能只选最好的一次。

## Helper 创建和实际引用

helper 是为完成固定目标而在本次运行中新建的辅助事实，不包括原有合法库引理和固定 contracts。保留声明、上下文、版本、创建事件、证明接受事件和消费者身份。对同名改写或重新尝试保留版本历史，不当成多个独立的新发现。

| 指标 | 定义与解释 |
|---|---|
| 创建数量 | 已落入生成工作区或正式局部图的不同 helper；仅提示中提出的意向另计 |
| 已证明数量 | 截止时存在有效原生证明证据的 helpers |
| 实际使用数量 | 在已检查消费者的证明依赖中出现的已证明 helpers |
| 多消费者使用 | 被至少两个不同消费者使用；同时区分消费者是 contract 还是 helper |
| 目标覆盖 | 通过直接或传递 helper 依赖实际支撑的固定 contracts |
| 跨 theory 使用 | 消费者与 helper 位于不同 theory，且通过合法上下文实际使用 |

依赖分析区分规划依赖、脚本中的显式名称、原生检查确认的依赖。引用优先从绑定已接受证明及上下文的原生证据获得；只在源码中搜索名称会遗漏自动化隐式使用，也可能把无效引用算进去。

每个运行报告依赖提取的覆盖率。没有提取到证据的 helper 标为“使用情况未知”，不能直接称为“未使用”。直接依赖与传递依赖分别计算，避免把一个中间事实展开成多次直接引用。

用创建、证明、实际使用的数量及其分布解释生成过程，再选取实际证明链展示如何支撑多个 contracts。创建更多 helpers、更多引用或更高共享率本身不代表更好；应结合目标完成和 token 消耗解释。该分析属于使用情况与成本分析，不能单独证明 helper 机制的因果收益。

## Token 消耗

总量以 provider 用量记录为准，按请求或累计快照去重。分别保留输入、缓存输入、输出和可获得的 reasoning 字段；缓存输入通常是输入的子集，reasoning 可能是输出的子集，按 provider 的具体语义归一化，不能重复相加。缺失用量记为 unknown，不填零。

生成阶段 tokens 包括失败尝试、检索后形成的输入、helper 工作、局部规划和修复。全局架构规划 tokens 单列，另提供全部已记录模型用量。费用按实际模型和计费语义另算；不同模型的 token 数不能直接等同于相同经济成本。

阶段归档可以区分目标证明、helper 工作、检索与诊断修复。一次响应可能覆盖多个目标或多个阶段，按实际记录的工作范围归档：多目标成本进入 shared，未声明范围进入 unattributed，不把同一请求重复分摊为多个目标的精确成本。

“总生成 tokens / 已证明 contracts”可作为整体摊销指标，但它包含失败目标和共享知识的成本，不代表单个成功证明的精确代价。零成功时该比值不适用。图表优先给出总量、阶段分布与完成曲线，并将未知用量占比放在对应结果旁。

## 论文结果组织

1. 主表展示三种方法在模型与数据集矩阵上的同时间生成结果，并列完整集成状态。
2. 划分消融表展示沿用原划分与自主划分的 contract 数量、生成 tokens 和规划开销。
3. 时间曲线展示各方法及两种划分在预算内如何积累有效证明。
4. helper 创建和引用图表展示知识如何产生、被证明并被实际消费。
5. token 分布图解释目标证明、helper 工作及共享探索的成本。
