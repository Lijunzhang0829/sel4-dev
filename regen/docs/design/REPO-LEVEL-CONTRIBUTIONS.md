# Repository-level 证明生成：问题、贡献与验证边界

本文依据当前已提交实现整理贡献，不将设计意图、局部测试和完整仓库验收混为一谈。实验性策略遵循各运行冻结的配置；未提交的 Vero 修改不计入本文。

## 1. 总体定位

Repository-level 证明生成需要协同构建跨 theory 的证明组织与合法上下文，使局部成果能够沿明确的依赖关系积累和消费；还需要验证 helper 分解对父目标的充分性，并约束过强或未降低推理负担的子义务，使困难证明的规划转化为可检查、可修订的执行过程。在此基础上，分层验收与恢复协议保障成果可靠积累，增量验证与跨 theory 并行降低执行成本。

本文将其分为五项相互配合的贡献：

| 贡献 | 核心问题 | 主要目标 |
|---|---|---|
| 可验证全局规划与消费评审 | 证明任务应如何划分，依赖应如何组织？ | 建立合法、可执行并考虑下游需求的组织 |
| 继承合法上下文的持续 theory 工作区 | 局部成果如何持续积累、检索和复用？ | 保持上下文一致，减少重复工作 |
| helper 组设计与 sketch 验证 | 分解是否覆盖父目标，是否值得投入？ | 验证组合充分性，控制过强或无效分解 |
| 分层验收与可恢复执行 | 如何确认整体成功，如何保留中断前的进展？ | 绑定正确性证据，恢复权威状态 |
| 增量验证与跨 theory 并行 | 如何避免检查和调度成本随规模失控？ | 复用检查成果，利用独立任务并发 |

前两项在研究问题上构成一个整体：**跨 theory 证明组织与合法上下文的协同构建**。工作区既承担正确性责任，也承担复用和上下文管理的效率责任。五项是实现贡献的组织方式，不表示五项均为已有研究中不存在的新技术。

## 2. 可验证全局规划与消费评审

### 问题与难点

固定 contracts 并没有给出完整的证明架构。系统仍需确定目标归属、硬依赖、潜在复用关系和执行顺序。证明依赖又不能完全从定义引用恢复：共享定义不等于存在有用的证明依赖，实际所需的辅助性质可能在证明过程中才显现。

规划合法也不等于消费方便。消费者只需要一个简单事实，却可能必须等待包含许多困难目标的提供者 theory 整体 seal。过度合并扩大阻塞范围，过度拆分则可能增加接口和上下文成本。

### 重要性

固定 theory 环境通常已经给定 imports 和前置事实；repo-level 生成需要自行组织这些条件。错误的组织会将局部困难扩散为跨 theory 阻塞，也可能使局部生成结果无法被需要它的消费者使用。

### 如何解决

1. 对初稿检查固定 contracts 的完整唯一覆盖、引用和依赖无环等约束。
2. 在冻结前评审消费者需要的结果、提供者边界和传递阻塞范围。
3. 对风险逐项决定调整规划、局部解决或保留，并记录理由与代价。
4. 修订后重新检查，冻结全局规划和产物身份；生成阶段维持全局边界，允许边界内的证明演进。

本次完整 Refine 规划保持 26 个 theories、287 个 contracts，将 `gcd_corres`、`curDomain_corres` 从 Runqueue_State 移到 Object_State，并删除 allocation 对 Runqueue_State 的硬依赖。该例说明消费检查能够提出实际边界调整，但不直接证明下游求解时间下降。

### 实现与验证边界

- [消费评审](../../planning/plan_review.py)、[评审修订流程](../../tools/reviewed_planning.py)。
- [实现说明](../implementation/PLAN-INTERFACE-REVIEW.md)。
- 合法性有明确检查；消费风险包含启发式判断，不保证发现全部缺失依赖，也不保证最优划分。
- 当前流程不采用窗口化规划或 root-theory proof pilot。

## 3. 继承合法上下文的持续 theory 工作区

### 问题与难点

多个 contracts 会共享状态性质、辅助引理和证明方法。逐目标孤立生成容易重复构造 helpers；无限累积对话又会增加上下文成本。更重要的是，草稿、临时假设、局部 GREEN 和上游已发布事实具有不同的可信性与可见范围。

修改 helper 或上下文后，旧消费者证据也可能失效。因此，“把文件放在同一个目录”不足以构成可靠的共享工作区。

### 重要性

repo-level 的收益依赖局部成果能被后续任务消费。若成果不能积累，任务规模扩大只会增加重复求解；若成果任意传播，则可能出现非法前提。共享必须同时满足可复用性和上下文合法性。

### 如何解决

- 每个 theory 使用持续源码文档和会话，维护草稿、已接受版本及诊断。
- 按冻结依赖继承合法上游上下文；局部事实按已接受前缀和实际可见性使用。
- 提供事实、定义、已接受证明示例和失败历史的按需检索，避免反复传入全部历史。
- 支持多个条目编辑和检查；修改已接受内容必须重新取得对应证据，失败草稿不替换已接受成果。
- theory seal 后按合法依赖提供成果；局部 helper 不会自动成为所有 theories 的全局前提。

### 实现与验证边界

- [共享工作区](../../execution/shared_proof_workspace.py)、[事实检索](../../execution/premise_recall.py)、[示例复用](../../execution/auxiliary_reuse.py)。
- [源码工作区说明](THEORY-SOURCE-WORKSPACE.md)。
- 检索命中不保证适用；复制示例仍须复验。当前不声称实现了通用 helper 自动泛化和全局最优复用。
- 可评价指标包括重复 helper 数量、实际消费数量、上下文 tokens、检索开销及复用后完成率；不能仅以工作区保存的 helper 数量衡量收益。

## 4. helper 组设计与 sketch 验证

### 问题与难点

helper 陈述合法、helper 可证、helper 足以支撑父目标，是三个不同的问题。一个成功证明的 helper 可能没有补上父证明缺口；一个能关闭父目标的 helper 也可能过强、不成立，或保留原问题几乎全部难度。

### 重要性

困难证明中的主要风险是长期投入一个未经验证的分解方向。无用 helper 消耗预算，过强 helper 放大难度，未覆盖父目标的 helper 组则使局部成功无法转化为父目标成功。

### 如何解决

1. 提交精确 helper 组及使用它们关闭父目标的消费者脚本，而不只提交 helper 名单。
2. 暂时假设该组成立，检查 `Γ, H₁, …, Hₖ ⊢ G`；条件闭合不发布真实证明事实。
3. 结合使用位置的变量实例、局部假设和所需结论，优先设计贴近实际需求的特化陈述。补充前提必须在消费者处满足；泛化可以为归纳服务，不一律禁止。
4. 通过结构分析与有限探测识别父目标重述、主要负担保留等风险。探测超时只表示预算内未完成。
5. 在相应实验策略中，将明确义务转入 `formal_leaf` 正式求解；脚本失败先局部修复，超过约定机会后显式修改消费者、接口或继续拆分。
6. helper 在合法环境中独立取得证明后，重新验收父目标；接口变化会要求消费者重检。

### 保证与非保证

**形式化保证是组合充分性及最终证明检查。** “不比父目标更难”目前不是可证明的准入性质；结构分析、特化策略和求解反馈旨在减少坏分解。这里的确定性是剩余义务、接口和检查结果明确，不是保证找到更容易的分解。

### 实现与实验边界

- [设计、接口与策略说明](../implementation/GUIDED-SKETCH-DECOMPOSITION.md)。
- 不同运行使用不同冻结策略，严格阶段转换和探测限制不能笼统视为全部默认行为。
- `tcbSchedDequeue` 的分阶段运行约 75.1 分钟完成，而旧 B 两小时未完成；但 `switchToThread` 虽减少 probe，总耗时和 tokens 反而上升。因此证据支持机制可行，不支持稳定普遍加速。
- 记录见 [dequeue 实验](../../../reports/regen/dequeue-phased-astra-20261016-001/REPORT.md) 和 [switch 实验](../../../reports/regen/switch-phased-astra-20261016-001/REPORT.md)。

## 5. 分层验收与可恢复执行

### 问题与难点

多个局部证明分别通过，不代表它们属于同一版本、使用一致上下文，或覆盖了完整任务。长程运行还会在检查、写入接受记录、更新摘要等不同位置中断；仅凭日志尾部无法恢复正确状态。

### 重要性

repo-level 任务中，一个过期接受结果可能被多个消费者使用；一次恢复错误也可能重复执行大量工作或漏掉尚未提交的成果。可靠性影响的不仅是速度，还包括最终成功声明是否成立。

### 如何解决

- 区分 batch/节点接受、完整 theory seal 和 repository integration。
- 将接受证据绑定到源码、陈述、上下文和依赖身份。
- 最终核对 contracts 完整唯一覆盖、实际 imports、seal 和发布源码，再在独立输出中整体构建；构建后复查输入一致性。
- 用持久提交和增量日志保存权威状态；进度摘要作为可重建投影。
- 保存检查请求和完成收据、消耗预算及恢复信息，区分证明失败与基础设施故障。

### 实现与验证边界

- [提交恢复](../../execution/proof_commits.py)、[检查任务](../../execution/check_tasks.py)、[集成验收](../../execution/repository_integration.py)。
- [增量日志与恢复测试](../implementation/INCREMENTAL-LOGGING.md)。
- 恢复不等于恢复原模型会话全部聊天状态，也不保证物理检查恰好执行一次。
- 强杀或主机故障后的残留进程回收仍有边界；环境内容由操作者保证稳定。恢复测试不证明任意故障下自动恢复。
- 该贡献建立在证明器已有检查和构建机制上，新增责任是生成任务及其成果的跨工作区一致性。

## 6. 增量验证与跨 theory 并行

### 问题与难点

每次局部修改若从头检查，验证成本会随文档增长。完全串行执行又浪费无硬依赖的独立任务之间的并发机会。但模型会话、活跃 Isabelle 检查与驻留热进程消耗不同资源；简单增加 workers 可能造成竞争或内存压力。

### 重要性

即使生成策略有效，检查和等待仍可能占据大部分墙钟时间。规模扩展需要同时减少重复检查与不必要等待，并保持证据和上下文隔离。

### 如何解决

- 复用未变化的已接受热前缀，检查受影响后缀；保留最终完整验收。
- 按硬依赖启动 ready theories，每个 theory 单写入、工具串行，不同 theories 并行；完成后补位。
- 独立限制活跃 theory 会话数、native 检查槽、Isabelle 线程及驻留 checker 数。
- 用独立任务目录、owner 和持久结果隔离并发输出；只有 seal 解锁硬依赖。

### 实现与验证边界

- [并行控制器](../../planning/parallel_file_planner.py)、[检查执行器](../../execution/check_executor.py)、[持久检查器](../../execution/persistent_checker.py)。
- [并行实现与测试](../implementation/PARALLEL-PIPELINE-IMPLEMENTATION.md)。
- 原生双任务 smoke 展示并发检查可行，不代表真实全仓生成具有相同比例的加速。
- 当前资源约束不等于基于实际 RSS 的完整内存调度。依赖关键路径、检查争用和模型时间都会限制并行收益。
- 后续应在相同模型、恢复点与预算下比较串行/并行墙钟时间、总计算成本、排队时间和峰值资源，不以 worker 数推断加速。

## 7. 与 theory-level 的关系及总体证据边界

这些问题在大型 theory 中也可能存在。repo-level 的新增责任是：系统需要自行组织多个上下文及其依赖，并确保局部成果通过这些边界积累，最终形成一致的完整仓库。因此不主张检查、工作区、恢复或并行本身是 repo-level 独有技术。

固定 contracts、语义环境构建、原始证明隔离与调用审计是实验可信基础。规划合法性和原生证明检查提供明确约束；消费评审和难度评估属于启发式方法；运行机制提供有边界的可靠性和效率保障。

当前已有实现、回归测试和局部实验，但新版完整流水线尚未完成全仓模型生成验收。不能将历史成功结果自动视为最新组合流程的验证，也不能将单例收益解释为因果确定的普遍提升。

## 8. 可用于研究介绍的贡献概述

我们构建了面向固定 contracts 的 repository-level 证明生成框架：首先，通过合法性检查与消费者需求评审形成冻结的全局规划，并以继承合法上下文的持续 theory 工作区支持成果积累；其次，以 helper 组及可执行消费者构成可检查的 sketch，验证分解充分性，并利用使用位置与求解反馈控制不适当分解；最后，以证据绑定的分层验收和持久恢复保障长程执行，通过增量验证及依赖约束下的跨 theory 并行减少重复检查和等待。各机制的正确性保证、启发式判断和效率收益分别评价，不以局部成功替代完整仓库验收。
