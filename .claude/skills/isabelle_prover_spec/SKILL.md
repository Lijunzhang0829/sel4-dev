# Spec type — strengthen the specification

Tis sub-skill **strengthens the statement itself**.The goal isn't faster build — it's a specification that catches more real
bugs, exposes more usable postconditions, and removes redundant noise.

Inherits the common contract from `isabelle_prover` (3 hard rules, common
tools, patch format, session mapping).

## Targets

| Path | Session |
|---|---|
| `spec/abstract/**` | `ASpec` |
| `proof/invariant-abstract/**` | `AInvs` |
| `proof/refine/**` (`_R` lemmas; statement-not-tactic changes) | `Refine` |

## Patterns — ordered by empirical ROI

Based on past sessions ([20260525](../../../reports/spec-strengthen/AInvs-20260525.md),
[20260526](../../../reports/spec-strengthen/AInvs-20260526.md)). Detailed
worked examples in
[`references/spec-strengthen-patterns.md`](../isabelle_prover/references/spec-strengthen-patterns.md).

| Pattern | Move | Empirical ROI | Risk |
|---|---|---|---|
| **C — Premise removal** | Drop a `valid_objs` / `invs` / `sym_refs` conjunct that the proof body doesn't use | **High** — every consumer call saves wp discharges | Low; if premise is load-bearing, `--patch` fails immediately |
| **B — Functional postcond** | Add `\<lbrace>\<top>\<rbrace> set_X v \<lbrace>\<lambda>_ s. X s = v\<rbrace>` | **Low immediate** — additive; no existing consumers benefit unless they currently unfold the def manually | Zero — pure addition |
| **E — Compound `_invs`** | Combine 5+ separate preservation lemmas into one `op_invs` | **High in theory, often infeasible in practice** — `invs` has 25+ components; missing any single `set_X_<comp>[wp]` blocks the proof | High; preflight check required (see below) |
| **A — Paired weak/strong** | Inline strong form or delete weak | **Near-zero downstream** — the weak form becomes an alias for the strong; consumers see equivalent postcond | **High false-positive rate (~70-80%)** — see warning below |
| **D — Loose bound → exact** | `≤` / `\<subseteq>` → `=` | Untested in this codebase | Variable |

### ⚠ Pattern A false-positive warning

Scanner-flagged Pattern A pairs are **wrong about 70-80% of the time**. Two
failure modes:

1. **Wrong direction** — the "weak" lemma is the granular building block,
   the "strong" lemma is a compound built FROM it (e.g. `cap_insert_invs`
   composes `cap_insert_valid_pspace`, `cap_insert_mdb`, …). Deleting the
   building blocks breaks the compound.
2. **Cross-op false positives** — two lemmas share a Hoare-body identifier
   (e.g. both wrap `set_cap`) but have incomparable preconditions; not
   substitutable.

**Always read both lemmas + grep cross-file usages before acting on a
Pattern A.** Pattern A is the LAST pattern to try, not the first.

### ⚠ Pattern E preflight checklist

Before attempting `op_invs` for an op X:

1. Does `op_invs_minor`, `op_invs_<variant>`, or `op_<state>_invs` already
   exist? Check via `grep '^lemma op.*invs' verification/l4v/proof/`. If
   yes, the gap is already filled — skip.
2. Does op have a `[wp]` preservation rule for **every** component of
   `invs`? Roughly 25 components including arch-specific ones
   (`valid_arch_state`, `valid_machine_state`, `valid_vspace_objs`,
   `valid_global_refs`, `valid_irq_handlers`, `pspace_in_kernel_window`,
   `cap_refs_in_kernel_window`, `pspace_respects_device_region`,
   `cap_refs_respects_device_region`, …). If any is missing, attempting
   `op_invs` will fail with "Unification bound exceeded" or "Failed to
   finish proof" — you'd have to add the missing preservation rules first
   (significant work).

The candidates file ranks Pattern E ops by *common* invariant count, but
that's a rough filter. Verify component coverage before committing.

## Targeting — read the candidates file

**Do not** read 4700 lines of `CSpace_AI.thy` by hand or rely on inline
file-richness rankings (they go stale as work is done). The ranked
candidates file is the targeting source of truth:

```
reports/spec-strengthen/candidates-<YYYYMMDD>.md
```

Generated by:

```
python3 tools/critical_path/rank_candidates.py --limit 30 \
  --out reports/spec-strengthen/candidates-<YYYYMMDD>.md
```

Re-run after a strengthening session to refresh the `[done]` markers and
demote lemmas already handled.

The candidates file is grouped by Pattern (C → E → B → A) and within each
group ranked by **consumer count** (downstream surface = ROI proxy).
Start at the top of Pattern C.

### Scanner reliability (calibration)

| Pattern | Scanner accuracy | Recommended validation |
|---|---|---|
| C — premise removal | ~50% (premise may be load-bearing) | `check-theory.sh --patch` is the cheap test (~60s) — fail fast |
| B — functional postcond | ~95% detection; but downstream consumer existence rare | Manual review for `unfolds set_X_def` in consumer proofs |
| A — paired weak/strong | ~20-30% real opportunities | Read both lemmas + grep cross-file before acting |
| E — preflight check | Component-coverage check before commit | See preflight checklist above |

The scanner ranks; the human judges; `check-theory.sh` is the only
acceptance gate. Treat scanner output as a work queue, not a verdict.

## Workflow (per candidate)

### Step 1 — pick from candidates file

Open the dated candidates file. Pick the top **un-done** Pattern C entry
unless you have a specific reason to do another pattern. Read ±20 lines
around `file:line` in the actual `.thy` file.

For Pattern A candidates: read both lemmas + run `grep -rln 'name' proof/`
on both names. Confirm the pairing is real and the direction is right
(see Pattern A warning above).

### Step 2 — draft the patch

Patch goes under `logs/spec-strengthen-<file>-<pattern>-<YYYYMMDD>.patch`.
Patch format described in `isabelle_prover` SKILL.md.

| Pattern | Move |
|---|---|
| C | Edit the existing lemma; remove the suspect conjunct from precondition. Proof body usually unchanged. |
| B | Insert a new lemma below the existing preservation lemma. |
| E | Add new compound lemma below the last preservation lemma. |
| A | Inline strong form, OR tag weak with `[wp del]` (conservative), OR delete weak (only if `grep` showed no cross-file users). |
| D | Replace `≤` / `\<subseteq>` with `=` in postcondition. |

### Step 3 — verify in isolation

```
bash $ISA_SCRIPTS/check-theory.sh <file.thy> <session>                  # baseline
bash $ISA_SCRIPTS/check-theory.sh <file.thy> <session> --patch <patch>  # trial
```

The patch must reach `OK`. **No `sorry` / `oops` / `axiomatization`.**

Note on wall times: baseline and trial differ ±5% from noise alone (JVM,
disk cache). Don't read into single-run timing differences; spec_impact's
gates use these only as a coarse regression check.

### Step 4 — measure impact (MANDATORY)

```
python3 tools/critical_path/spec_impact.py <patch> <file.thy> \
  --baseline-wall <ms> --trial-wall <ms> \
  --tree verification/l4v/proof \
  --append-to reports/spec-strengthen/<session>-<YYYYMMDD>.md
```

The report is appended to your dated strengthen-log automatically. Gates:

| Gate | Required |
|---|---|
| No `weakening` verdict | HARD STOP |
| ≥ 1 lemma with one of `premise-weaken` / `monotone-strengthen` / `postcond-strengthen` / `additive` | yes |
| Trial wall ≤ baseline × 1.30 | yes (noise tolerance; ±5% is normal) |

**Verdict interpretation (use this to prioritize):**

| Verdict | Pattern | Downstream ROI |
|---|---|---|
| `premise-weaken` | C | **✓✓ High** — every consumer discharges fewer premises |
| `monotone-strengthen` | C + post-grow | **✓✓ High** (combines both) |
| `postcond-strengthen` | A "dedupe" | **Low** — consumers may need to weaken back |
| `additive` | B / E | **Opt-in only** — no existing consumers affected |
| `rewrite` | — | manual review needed |
| `weakening` | — | **abandon** |

### Step 5 — apply

```
bash $ISA_SCRIPTS/check-theory.sh <file.thy> <session> --apply <patch>
```

**Important**: `--apply` writes the source file but does NOT rebuild the
session heap. The session heap still holds the OLD lemma signature until
the next full `isabelle build`. Consequences:

- `check-theory.sh ARM/Other.thy AInvs` after `--apply` runs against the
  OLD heap → it does NOT measure the strengthening's downstream impact.
  It only checks syntactic compatibility with the OLD signature.
- The actual wp-engine work reduction (the real ROI) only materializes
  AFTER a full `isabelle build AInvs`. Budget hours.

**Recommended cadence**: don't rebuild AInvs after each patch. **Batch
5-10 strengthenings** then do one full session rebuild, then measure
session-total wall vs the pre-batch baseline. Single-patch downstream
measurement costs ~80 min for ambiguous numbers in the noise band.

After `--apply`, prepend one short paragraph to the auto-appended impact
block in the strengthen-log:
- Pattern letter
- One sentence on what the strengthening enables downstream
- Whether a session rebuild has been done (default: not yet)

## Acceptance

Apply iff the Step 4 gates all pass and the statement is **strictly more
informative** (weaker pre, stronger post, or both — Tier 1 numbers
confirm). The 3 hard rules from `isabelle_prover` (no `sorry` / `oops` /
`axiomatization`, check-theory.sh as only gate, etc.) are inherited.

Spec strengthening trades build time for verification strength — a
slightly slower build with a stronger spec is the intended direction.
