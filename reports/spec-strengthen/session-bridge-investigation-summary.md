# Session summary — the "proof bridge" investigation

Branch: `bridge-consumer-trace`. Date: 2026-06-14 → 2026-06-15.
Theme: from "make the proof build faster" to "make the spec↔Haskell↔C **bridge**
cheaper to re-establish after a change," grounded in one experiment + a real
case study + a three-pass literature survey.

## Narrative arc

### 1. Reframing the goal (discussion)
Starting question: should we make the proof that bridges spec/Haskell/C **faster**?
**Verdict: no.** Two distinct costs:
- **latency** (wall time of a re-run) — already shown to have **no LLM leverage**
  (project memory: tactic static-ization / search-elimination = noise);
- **fragility** (labor to re-establish a broken bridge) — the real, *compounding*
  cost for a project whose premise is "make many spec/Haskell/C changes."

Unifying model: a change's cost lives in three buckets on a **cheapness gradient**
— **rewrite (human/LLM) → re-search (automation) → re-check (machine) → 0 (no
invalidation)**. Optimization = push cost *down* the gradient, not make any one
bucket "faster." The LLM's unique seat is the top (rewrite, and rewrite→re-search
via consumer-first lemma generation); everything below is infra/design.

### 3. The re-check / re-search / rewrite model (discussion)
Corrected the intuition "a change just re-runs / re-searches":
- **re-check** = machine re-verifies *everything* downstream (heap dependency),
  even unchanged proofs;
- **re-search** = automation (`simp`/`wp`/`auto`/`ctac` leaves) re-derives against
  a changed goal *without edit* — but only if needed facts are in scope;
- **rewrite** = explicit structural scripts that don't re-search must be edited.
How to measure the ratio in seL4 (no prior study reports it; it's a distribution
over change-classes, not a constant): **M1** mine l4v git history (rewrite churn
per source change — cheap, but the local checkout is depth-1, so target upstream
`seL4/l4v`); **M2** controlled ablation (apply source change, withhold proof edits,
rebuild → fail=rewrite, pass+goal-changed=re-search, pass+goal-same=re-check).

### 4. The setThreadState case study (real l4v code)
Pulled the real four-layer artifact and annotated the **corres proof as a line-by-
line mirror of the Haskell body** (`TcbAcc_R.thy:3181`, `IpcCancel_C.thy:2185`).
- **★ positional-structural lines** (`corres_split[OF …]`, `ctac add:`, `corres_if`)
  match by pattern → **rewrite-fragile**;
- **☆ automation legs** (`simp+`, `wp … | simp +`) → **re-search-capable**.
- Three traced scenarios: (A) behavior-preserving **reorder** still forces a
  rewrite (positional chain) — refutes "just re-run"; (B) a change landing in an
  automation leg is **re-searched for free** *iff* the needed fact is in scope
  (else rewrite) — this is exactly what consumer-first frame lemmas pre-position;
  (C) **guard change** breaks the equivalence sub-proof and, if abstract isn't
  changed in tandem, the corres statement itself is false (escalation, "type-5").

### 5. Haskell/C optimization-direction judgment (discussion)
Read both sub-skills (`isabelle_prover_haskell`, `isabelle_prover_c`). Cost
geometry **inverts the apparent priority**:
- **C is where optimization belongs** — deployed artifact, contained-ish blast
  radius; rank C opts by **re-establishment Tier**, not code benefit (T1: lifts to
  same/simp-equivalent term → re-search, free; T2: control-flow change → ctac
  rewrite, repair-loop sweet spot; T3: struct/relation change → escalate).
- **Haskell optimization is mostly a trap** — design spec isn't deployed, so perf
  optimization is moot, and clarity refactors pay the **double bridge** (Refine +
  CRefine) for zero runtime gain. Only justified as a *paired enabler* of a C
  change or to fix a modeling deficiency.

### 6. Three-pass literature survey (ran; deep-research)
See [literature-baseline-haskell-c-optimization.md](literature-baseline-haskell-c-optimization.md)
for the full cited baseline. Headlines:
- **Confirmed our framing**: C chosen over auto-translated Haskell *specifically
  to preserve micro-optimization* (TOCS'14); "cost of change" = **17% of proof
  effort for <5% code** (reply caps, SOSP'09); fastpath sideways-equivalence =
  the existing optimize-then-reverify template (**5 person-months**).
- **NEW**: C→binary translation validation (Sewell et al. PLDI'13, graph-refine)
  is a **third re-establishment layer** (~6–8 h, **optimization-level-sensitive**:
  full -O1, ~98% -O2) → sharpens the C Tier model with a TV gate.
- **Gap real**: proof-repair automation exists **only for Coq** (PUMPKIN Pi;
  **Sisyphus PLDI'23** = closest prior art, repairs proofs after *arbitrary
  implementation change, unchanged spec*, all 10 benchmarks) or **push-button SMT**
  (Serval — provably doesn't scale to seL4). **No work repairs Isabelle refinement
  proofs; no ML/LLM work on seL4 refinement repair.** PUMPKIN Pi *names seL4 as
  motivation but does not apply to it.*
- **Area 6 (pass 3)**: multi-arch ports + MCS are real large co-evolution events
  but **porting cost is genuinely unpublished**; arch-split payoff is *intent, not
  measured*; MCS C-verification targeted **Q3 2027**; binary verification still
  ARM32/RISC-V64 @ -O1 (AArch64/-O2 are future "Beyond" goals).

## Where this lands

The investigation **confirms the strategic thesis with primary sources**:
1. The bridge's cost is **re-establishment labor**, not wall time, and it is
   **large and recurring** (17%/<5%; 5 pm/fastpath; 6–8 h binary TV per C change).
2. C is the right optimization layer but carries **two machine re-establishment
   layers** (CRefine + binary TV) and a **compiler-optimization-sensitive** TV gate.
3. **LLM-driven repair of seL4 refinement proofs after Haskell/C changes is a
   genuine open niche** — *named* (PUMPKIN Pi), *validated in an analogue*
   (Sisyphus, Coq), but **never built for seL4/Isabelle**.

## Recommended next actions
- **Highest leverage**: pivot the frame-lemma machine to **consumer-first** (drive
  generation from real broken obligations; KPI = downstream auto-close rate, not
  wall delta).
- **Prototype**: the dual-use **blast-radius localizer** (the haskell skill's
  translate-and-verify + the C skill's c-impact, unified) — static, no heap risk,
  feeds Tier prediction.
- **Skill update**: add the **translation-validation Tier gate** to
  `isabelle_prover_c`; foreground the **paired Haskell+C** workflow as the only
  legitimate Haskell use.
- **Frontier (the open niche)**: a Sisyphus-style **refinement-proof repair loop**
  for corres/ccorres, soundness-gated (no admits, statement-identity, full
  downstream green).
