# Bridge consumer trace — are the 52 applied frame lemmas actually consumed?

Branch: `bridge-consumer-trace` (investigation, meta-PR variant).
Date: 2026-06-14.

## Question

The spec-strengthen line has applied **52 `[wp]` frame lemmas** (exp 0014–0054),
all of the shape "operation X does not change state field Y", proven by a
one-line `wpsimp`, verdict `additive`, wall delta in the ±noise band
(−0.7%, −3.8%, …). Hypothesis under test: these were generated by
*enumeration* (every field × every op), not pulled by a failing downstream
obligation — so they may be **speculative additive** (no real consumer).

The refinement chain they are supposed to serve:
- AInvs (invariant-abstract) — where the lemmas live and are proven.
- Refine (spec↔haskell corres) + CRefine (haskell↔c ccorres) — the actual
  *bridge*, which consumes AInvs `[wp]` rules implicitly via `wp`/`wpsimp`.

## Method + results

### 1. Explicit (named) consumers — grep, whole `proof/` + `spec/` tree

For each of the 52 lemma names, word-boundary grep across all `*.thy`,
excluding the definition line.

**Result: 0 / 52 have any explicit named reference anywhere.** Each lemma
appears exactly once — at its own `lemma NAME[wp]:` definition. No proof
step names them via `using` / `rule` / `wp:` / `simp:`.

Caveat that makes this *necessary but not sufficient*: these are `[wp]`
rules. Their entire design is to be picked up **implicitly** by the `wp` /
`wpsimp` method without being named. grep is structurally blind to implicit
`[wp]`-set consumption. So "0 named consumers" ≠ "0 consumers".

### 2. Same-file ablation — `set_thread_state_arch_state[wp]`

Removed the lemma (TcbAcc_AI.thy:1490–1492) and rebuilt the file under AInvs.

- baseline (unpatched): `OK (70879ms)`
- ablated: `OK (72274ms)`

**Building TcbAcc_AI without the lemma still succeeds.** ⇒ no consumer of
this lemma exists *within its own theory*.

> Note (skill rule #4 in the wild): the **first** ablation run reported a
> spurious `FAILED (36654ms)` caused by an orphan
> `/tmp/isabelle-session-AInvs.lock` left by a prior run — a transient
> search-explosion-guard misfire, not a real proof failure. Two clean
> re-runs both returned OK. Lesson logged: always clear stale session
> locks before trusting an ablation verdict.

## What is established vs. open

| Scope | Consumer of the frame lemmas? | Confidence |
|---|---|---|
| Explicit named refs, whole tree | **none (0/52)** | high (grep, reliable) |
| Within own theory (TcbAcc_AI) | **none** (ablation OK) | high (2 clean runs) |
| Downstream AInvs files importing it | unknown | — needs full AInvs ablation |
| **Refine / CRefine (the bridge)** | **unknown** | — needs cross-session ablation (~1h+/session, heap risk) |

The cheap evidence leans toward **speculative additive**, but the decisive
question — does the *bridge* consume them — is not yet answered. It requires
ablating the `[wp]` rule out of the AInvs heap and rebuilding Refine/CRefine,
which is the expensive, heap-volatile path (skill rule #4: budget hours,
never pkill).

## The methodological finding (independent of the open question)

Even if some lemmas turn out to be consumed downstream, the project **cannot
currently tell which** — because they were generated blind (enumeration),
not consumer-first. Answering "is this lemma load-bearing?" today costs a
full-session ablation per lemma. That is the real gap.

**Recommendation (consumer-first generation):** drive frame-lemma generation
from *real broken obligations* — make a change at a node, let Refine/CRefine
break, read off exactly which `[wp]`/frame rules the broken obligations need,
and add only those. Every lemma then has a provable consumer by construction,
and the KPI shifts from `wall delta` (noise) to **downstream auto-close rate**
(how many bridge obligations now discharge by `wpsimp` that previously did
not). This is the "self-healing bridge" loop.
