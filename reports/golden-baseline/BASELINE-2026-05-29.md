## 4. Per-session parallelism factor commentary

- **High factor (≥ 1.9)**: 14 sessions. Best is `CRefine` at 2.37, then
  `CRefineSyscall` at 2.18, `AInvs` at 2.03, `DSpec` at 2.05. These
  sessions are intra-session-parallel-friendly (theory DAG within the
  session has many independent branches).
- **Moderate factor (1.4-1.9)**: 13 sessions. Most of the medium and
  large sessions; gains diminish as theories become more sequential.
- **Low factor (< 1.4)**: 2 sessions:
  - `AutoCorresSEL4` (1.19) — bottlenecked on a single large theory
    (`TestSEL4`) that monopolizes its own runtime.
  - `Pure` (0.98) — initial bootstrap; tiny single-threaded.
  - (`SimplExport` at 1.07 — IO-bound on export.)

## 7. Hardware comparison vs upstream

The seL4 CI's actual EC2 instance type is private (encapsulated in
`l4v-runner` launch template), but their `run_tests -j 2` setting plus
the l4v README recommendation (~16 GB RAM, ~8 cores useful) give context.

| dimension | upstream l4v README | seL4 CI (probable, from `-j 2` + private instance) | this baseline |
|---|---|---|---|
| RAM | "~16 GB" | likely ≥ 32 GB (else `-j 2` for AInvs/CRefine OOMs as we observed) | 29 GB ⚠ tight for `-j 2` without `--maxheap` cap |
| cores | "8 useful" | unknown | 16 (2× recommendation) |
| `-j` | not specified | 2 | 2 |
| `--maxheap` | "don't constrain" | unknown | required `--maxheap 12000` on 29 GB host |

Our 29 GB / 16 cores **exceeds the README recommendation** on cores but is
on the edge for `-j 2` RAM. The `--maxheap 12000` constraint is what
makes our `-j 2` feasible; without it, AInvs + CRefine concurrent will
OOM on 29 GB (validated 2026-05-28).

## 8. Reproducibility

The baseline ships these artifacts:

```
reports/golden-baseline/
├── RECORD-PLAN.md            (pre-build plan)
├── BASELINE-2026-05-29.md    (this file)
├── walls.json                (per-session timing + config)
├── env.json                  (build environment snapshot)
├── heap-sizes.txt            (SHA-256 fingerprint per heap)
├── lemma-inventory.db        (SQLite, 36 567 lemmas)
├── lemma-inventory-summary.md
└── build-logs/
    └── round1.log            (full tee of isabelle build output)
```

To reproduce on a different host:

1. Restore `verification/l4v` to `00d9073f` (clean working tree)
2. Set `/root/.isabelle/etc/settings`:
   - `ML_OPTIONS="--maxheap 12000 --stackspace 64"` (adjust upward if RAM > 32 GB)
   - `export SKIP_DUPLICATED_PROOFS=1`
   - `export ISABELLE_BUILD_OPTIONS="document=false"`
3. Wipe `/root/.isabelle/heaps/polyml-5.9.1_x86_64_32-linux/` (fresh start)
4. Run:
   ```
   L4V_ARCH=ARM isabelle build -b -j 2 -v -d <l4v-path> \
     Refine CRefine CRefineSyscall DRefine DPolicy DBaseRefine DSpecProofs \
     InfoFlowC RefineOrphanage Bisim SimplExportAndRefine SepDSpec \
     AutoCorresSEL4 Access InfoFlow
   ```
5. Run `python3 tools/golden_baseline/extract.py`

Per-heap SHA-256 will differ from this baseline (polyml serialization is
platform-dependent), but wall numbers should be comparable for hosts of
similar core count + RAM + `-j 2`-suitability.

## 9. What this baseline is fit for

- **Diffing against**: yes — any spec-strengthening experiment claims of
  wall impact should compare to `walls.json` numbers, and any source
  change should produce a `lemma-inventory.db` diff via
  `tools/lemma_inventory/diff.py` showing what changed.
- **Reporting absolute numbers in a paper**: yes — this is now the only
  known publicly-reproducible seL4 full ARM build measurement with
  documented hardware and config. 0 / 10 academic papers (2021-2026)
  report comparable detail (per agent survey 2026-05-29).
- **Sanity-checking later builds**: yes — the heap SHA-256 chain plus
  lemma-statement SHA-256 chain together pin both binary and source
  state. A future build whose heap fingerprints differ but whose lemma
  inventory matches has identical source but different binary; one
  whose lemma inventory differs has source drift.

## 10. Known caveats

1. **Hot-cache wall numbers**: per-session walls assume parents are
   already in heap. A from-scratch single-session build of e.g. CRefine
   alone would be longer (~2:48 + parent build time).
2. **`--maxheap 12000` is non-stock**: maintainer email says don't
   constrain heap; we do because the alternative is OOM. Higher-RAM hosts
   can lift the constraint.
3. **The 14h "sum of session walls" is meaningless as a wall metric**:
   it counts each session's wall in isolation, ignoring the parallelism
   that produced the actual 7:55:34. Don't add walls.
4. **The 36 567 lemma count includes utility/library sessions** (Lib,
   AutoCorres, Sep_Algebra) which are not all explicit build targets but
   are scanned because their .thy files are reachable from ARM ROOT files.
   Kernel proper is ~25 000 of those.
