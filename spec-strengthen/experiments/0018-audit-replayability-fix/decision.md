## Scope

User 2026-06-03 asked to **verify the full chain** of the four
applied experiments end-to-end. The audit caught a real bug in
the audit-dir `patch.diff` files for [[0015]] / [[0016]] /
[[0017]]: they were syntactically broken unified diffs and
**could not be replayed via `git apply`**.

The actual source changes in `verification/l4v/` are correct —
the `check-theory.sh --apply` chain landed them properly and
they appear in the file. The bug was only in the audit-dir
records, not in the deployed source. But per parent SKILL rule
5, `patch.diff` is **the canonical replay artifact** — a broken
one defeats the audit-trail's purpose.

This PR fixes the audit dirs only.

## What was broken

### Bug 1 — empty context lines missing leading space

I hand-wrote three unified-diff files via the `Write` tool. In a
unified diff, **every line in the hunk body must start with one
of `<space>`, `+`, `-`**:
- `<space>` for context (lines present in both sides)
- `+` for added lines
- `-` for removed lines

An **empty source line that is context** must be `<space>\n` (a
single space then newline) — **not** just `\n` (bare newline).
My hand-written patches emitted bare empty lines, which `git
apply` rejects with `补丁在第 N 行损坏` ("patch corrupted at line
N").

### Bug 2 — wrong `@@` hunk-header line counts / offsets

When I tried to fix Bug 1 by extracting the latest experiment's
hunk from a **cumulative** `git diff` (the diff between current
state and the submodule baseline `00d9073f70d0`), the extracted
hunk's `@@ -L,N +L',N' @@` header carried line numbers from the
cumulative view, not the per-experiment view. Specifically
[[0015]]'s extracted hunk said `@@ -3844,6 +3848,10 @@`, but the
file at `[[0014]]-applied` (the actual base for [[0015]]) had
the context starting at line 3848, not 3844 — a 4-line offset
caused by [[0014]]'s inserted 4 lines at line ~432.

`git apply` correctly refused: the source-line numbers didn't
match.

## The fix — capture each diff against its actual base

For each experiment N, the audit dir's `patch.diff` MUST be
`diff(file at applied-state-of-N-minus-1, file at
applied-state-of-N)`, regardless of how many strengthenings came
before.

Mechanism (replayable forever):
1. Take a snapshot of `/tmp/CSpace_AI.thy.applied` (current
   state, all 4 lemmas in place).
2. Reverse-apply each subsequent experiment to compute pre-state
   snapshots (`/tmp/state_pre_0015.thy`, `/tmp/state_pre_0016.thy`,
   `/tmp/state_pre_0017.thy`). For the two middle experiments
   where reverse-apply via the broken patch wouldn't work, I
   used Python regex to surgically remove the relevant lemma
   block from the captured state — this gives the exact same
   bytes as a clean reverse-apply would have.
3. Run `diff -u <pre> <post>` for each pair.
4. Prepend the `diff --git a/...b/...` header that `git apply`
   needs.
5. Restore the file to the all-4-applied state.

This produced four `patch.diff` files that:
- Reverse-apply cleanly **in order 0017→0016→0015→0014**, leaving
  the file at submodule baseline (0 strengthening lemmas).
- Forward-apply cleanly **in order 0014→0015→0016→0017**, leaving
  the file byte-identical to the originally-applied state
  (`/tmp/CSpace_AI.thy.applied`).

The 4-line `+N` vs `+N+3` asymmetry in the new headers is correct:
- [[0015]] adds 3 net lines (lemma signature + 1 statement + 1 proof — counts only the lemma body, not the trailing blank that exists in both pre and post states for crunch separation).
- [[0016]] adds 3 net lines (same shape, same count).
- [[0017]] adds 4 net lines (the new lemma block + its trailing blank is what `diff -u` counted, vs [[0015]]/[[0016]] where the trailing blank was already present in the file's "crunch vms[wp] ... \n\n\n" sequence).

This is honest record of what the file actually looked like at
each step, not a fabricated symmetry.

## Notes / follow-ups

- **Workflow improvement for future experiments**: when applying
  a chain of related strengthenings to the same file, **snapshot
  the file before each `--apply`** and capture `patch.diff` via
  `diff -u <pre> <post>` immediately. Generating `patch.diff` by
  hand-extracting a hunk from a cumulative `git diff` against
  the submodule baseline is fragile (line-number offsets
  accumulate; this is what hit me). Consider adding a thin
  helper `tools/spec_strengthen/spec_capture_patch.sh
  <experiment-dir> <theory-file>` that automates the snapshot
  + diff step. Out of scope for this audit PR.
- **decision.md text in [[0015]] / [[0016]] / [[0017]] is
  unchanged** — the description of what each experiment did, why,
  and the impact remains accurate. Only the `patch.diff` byte
  content changed (now syntactically valid).
- **The deployed source was never broken** — the bug was
  documentation-side only. `check-theory.sh --apply` used the
  **range-replace patches** in `logs/` (which were always
  correct, since they round-trip through Isabelle), not the
  unified diffs. The unified diffs only matter for replay /
  audit.
